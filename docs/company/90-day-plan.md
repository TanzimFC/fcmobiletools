# First 90 Days

The aim is to build a small, dependable operating team without increasing costs or distracting from the website.

## Days 1–14: establish control

- [ ] Confirm the owner, department responsibilities and decision limits.
- [ ] Publish volunteer policy and role descriptions.
- [ ] Create a private contributor/access register.
- [ ] Create a single task backlog using GitHub Issues and Projects if already available.
- [ ] Record current website, hosting, database, analytics and notification providers.
- [ ] Document critical paths: release, rollback, redeem-code update and incident escalation.
- [ ] Establish baseline metrics using existing analytics. Mark gaps clearly.
- [ ] Start a zero-based cash ledger with opening balance and $0 spending authority.

**Exit condition:** every active task has an owner, each critical service has a named maintainer, and privileged access is known.

## Days 15–30: recruit and test the system

- [ ] Recruit 2–4 reliable volunteers for specific bounded roles.
- [ ] Give each contributor a small trial task and named reviewer.
- [ ] Start weekly reports and a short weekly leadership review.
- [ ] Test the core user journeys: homepage, critical tools, account flow where applicable, redeem-code pages and mobile navigation.
- [ ] Complete the first access, content accuracy and financial-control checks.
- [ ] Publish the first monthly company report, including missing measurements.

**Exit condition:** reports contain evidence, key issues are tracked and contributors understand permissions and expectations.

## Days 31–60: improve consistency

- [ ] Assign function leads only where sustained workload justifies them.
- [ ] Add regression checks for frequently broken user journeys.
- [ ] Establish editorial source and correction records.
- [ ] Review onboarding, response times, contributor workload and retention.
- [ ] Resolve critical and high audit findings or document safe containment and a dated remediation plan.
- [ ] Build a simple record of growth experiments and their actual outcomes.

**Exit condition:** routine work can proceed without the founder directing every small task.

## Days 61–90: evaluate and adjust

- [ ] Review which volunteer roles produce consistent, useful outcomes.
- [ ] Remove unused access and stop recurring work that has no clear benefit.
- [ ] Compare analytics against the original baseline using identical definitions and periods.
- [ ] Review financial records, dependencies, recovery procedures and unresolved risks.
- [ ] Publish a 90-day review: shipped work, reliability, growth, people, costs, failures and next priorities.
- [ ] Keep the structure small; do not create titles or departments without actual work.

**Exit condition:** the owner has a reliable view of product health, volunteer capacity, unresolved risk and actual cash position.

## Priority rule

When capacity is limited, work in this order:

1. Security, privacy and serious user-impact incidents.
2. Broken core tools, login or essential site journeys.
3. Accuracy of redeem codes, event dates and important guides.
4. Maintenance that prevents repeat failures.
5. Growth experiments with a measurable outcome.
6. Cosmetic work and speculative features.

The plan does not require paid software, paid advertising or a promise of future salaries.
